# Output-style rule history

Why some of the rules in `assets/personas/clear/output-style.md` exist. These
notes were written while the rules also lived in `references/guardrails.md`,
numbered as guardrails, so the numbers below are that file's. The file was
retired on 2026-09-27, and the output style is the one copy of the rules now.
The numbers no longer match the style's own. The reasons still do.

**Why question delivery is guardrail 11.** Rule 1 has always required three options and a recommendation before a change, and until rule 11 shipped it said nothing about *where the user reads them*. That silence had a measurable cost: options and questions landed in the middle of a long reply, scrolled away under the output that followed, and the work sat stalled on an answer nobody knew was wanted. Rule 11 names the channel. Anything that blocks or forks the work is asked with `AskUserQuestion`, which renders as a prompt rather than as prose — and in an unattended session it *pauses the run and waits* instead of fabricating an answer, the same property `/workbench-core:propose-upgrades` relies on for its nightly sign-off triage. A question with no multiple-choice shape, or a context where the tool is unavailable, falls back to a `## ❓ Open questions` block placed last in the response, after the verdict. Last is the whole point: anything printed below a question is what buries it. That fallback was retired on 2026-10-05. The last entry below says why.

**Why finding verdicts are guardrail 12.** Rule 1 binds at action boundaries, and scopes itself that way in its own ✅ example. Rule 11 binds on open questions. A finding that proposes no action and asks no question triggers neither of them, so it reaches the user as a bare fact. Closing a release, that produced two real findings reported as "neither is urgent": no verdict on whether either was a problem, no options, and no recommendation. The user had to ask what to do with them, which is the work that should already have been done. Rule 12 binds the moment you notice rather than the moment you act. Report what it is, whether it is a problem, how bad, the options, and which one you recommend. Severity is not a verdict, because "not urgent" answers when and never whether, and "unknown" answers neither. "No action needed" is a valid verdict and gets stated rather than dropped.

**Why question contents are guardrail 13.** Rule 11 named the channel and said nothing about what travels down it, so a bare numbered list of questions satisfied every rule then written. Three separable failures shipped that way. The agent stated a fact whose next step depended on an answer, and never turned it into a question. It framed a fork as a problem, which sends the reader hunting for a defect that is not there. And it printed questions with no situation attached, leaving the reader to reconstruct what each one was about before answering any of them. Rule 1 already carried the shape — three options and a recommendation — but scopes itself to "before making changes", so a question about anything else inherited no shape requirement at all. Rule 12 does not cover the gap either: its report order is problem-shaped ("whether it is a problem, how bad"), which leaves a neutral fork no honest form to be reported in. Rule 13 binds all three halves — recognize, frame, shape — in whichever channel rule 11 selects. It appends rather than extending rule 11 in place, because rule 11 already carries four concerns and a fifth is easier to apply halfway.

**Why option layout is guardrail 14.** Rules 1, 12 and 13 each require three options and a recommendation, and none of them said what that looks like on the page. So the layout was invented fresh every reply, and the last drift produced a form the user reported as hard to read against one that used to be clean: a different medal glyph on each option, titles shortened to fragments, and the recommendation folded into the option it picked, where it has to be hunted for. Rule 14 pins the shape. Each option is its own markdown heading rather than bold text inside a paragraph, because a heading is rendered in color and that color is what the eye finds first. The heading carries the marker 🔹, the word "Option" with a spelled-out letter, and a short descriptive title. Under it go that option's pros and its cons, both every time. After all three, a separate paragraph names the recommendation and gives its reason.

The marker is one glyph repeated, not a set, and that is the half with a measurement behind it. An earlier draft used 🅰️ 🅱️ 🅲 and it renders three different ways: 🅰️ and 🅱️ are U+1F170 and U+1F171 with a variation selector and come out red as blood-type emoji, while 🅲 is U+1F172, has no emoji presentation form at all, and falls back to gray text. The first two also put a variation selector over an East-Asian-Width-Ambiguous base, which is the exact class Terminal.app miscounts the width of. 🔹 is U+1F539: natively Wide, no variation selector, identical on every option. The letter carries the sequence, so a per-option glyph set cannot come back the moment someone needs a fourth option. Rule 14 also sets the tiebreak the recommendation uses, which no rule stated before: correctness outranks speed of implementation, so the recommendation is the architecturally correct option and says plainly when that one is also the slower one. It appends rather than extending rule 1 in place, for the reason rule 13 appended rather than extending rule 11: rule 1 already carries five concerns, and layout is referenced by rules 12 and 13 as well, so it needs to be somewhere all three can point at.

**Rule 9 grew a clause in the same pass**, for the mirror-image failure. "Lead with what is wrong or risky" is an ordering instruction, and nothing said it was *only* an ordering instruction. Three sub-agent findings were relayed as three costs when one of them was an improvement and one was a fix, so three commits of good work read as a list of concessions. Order by risk, label by fact: those are two operations, and a cost is specifically something the reader is worse off for. A behaviour change, a stricter check landing somewhere more reliable, and a correctness fix that widens what is accepted are none of them costs.

**Why rule 6 grades against acceptance criteria, and points at intake (2026-09-29).** Rule 6 had replaced "always present three options" with "offer options only where they earn their place", and asking had become a fallback for vague requests with nothing that made it a step. Together with research-before-asking, a "blocking uncertainty only" bar, and two vault notes against re-asking, the agent stopped asking at all. The fix was a routine rather than a louder rule, so it lives in `skills/intake/SKILL.md` and the style carries only a pointer to it. The routine drafts and grades three options for every task that produces work, and puts them to Mike only at a real fork, so rule 6's "offer" still holds as written. The one change is to the recommendation: when a task has acceptance criteria, its reason is each option's grade against every criterion, because a reason that cites no criteria cannot be checked against what the task was for.

**Why replies have a screen budget, and decisions go through the tool (2026-10-01).** Mike reads the main session in a terminal about 80 columns wide and 50 rows tall. Replies ran long enough that the explanation, warning, or option a later line referred to had already scrolled off, and that was worst exactly when he had to decide something. The length came from the rules themselves. Rule 6 rendered each of three options as its own `### 🔹 Option` heading with pros and cons, about 25 to 30 rows before the recommendation. Rule 2 said the reason "outranks brevity" with no upper bound. The intake routine printed its block, then the options, then a grade per criterion, so the criteria scrolled away before the grades named them. Replies also said "as noted above" about text that was no longer on screen. Rule 12 sets a budget of about 40 rows and puts the item Mike acts on last, restated so it stands on its own. The placement of a question in that clause was replaced on 2026-10-06, and the last entry says why. Rule 6 now renders the three options as one table. Rule 2 keeps the reason and bounds it to one per point. Rule 4 and the intake skill send every decision through `AskUserQuestion`, whose option descriptions carry the grade and any warning. Moving long content out to files as a standing practice was considered and not chosen. The 🔹 marker recorded under guardrail 14 above no longer appears in the style.

**Why rule 6 names the commit approval (2026-10-01).** Rule 6 exempts commits and ordinary pushes from its three options. Since 0.42.0 the exemption also said to attempt them, "because the approval gate prompts Mike", and 0.44.0 shipped that sentence again. Read literally, it made Claude Code's permission prompt the approval. A Holmes review flagged it. The prompt is only a mechanical backstop, and a prompt that appears mid-flow gets answered without a review. Mike then set the rule. The foreground session asks one approval question through `AskUserQuestion`, on its own, after he has reviewed the tree. His answer is the approval, and a typed "commit it" in chat was no longer the mechanism, until Mike reversed that on 2026-10-15 (below). A sub-agent never commits or pushes. It hands back the tree and a proposed message, and the orchestrator asks. An Index pipeline run commits and pushes unattended and never asks. The exemption from three options stays, because a commit needs one question and not a fork. Other prose carried the same false expectation, and now names the question as the approval. `skills/propose-upgrades/SKILL.md` said the user commits "through the approval gate". The README said repo-file changes "still pass through the normal commit-approval gate". Three passages read as if the commit gate were the approval. The README said integration "goes through the development flow and the commit gate". `skills/compact-learnings/SKILL.md` said a hand-copied change "skips the development flow, its tests, and the commit gate". `skills/propose-upgrades/SKILL.md` said "Repo changes go through Watson and the commit gate". That skill also said "user commits" in its proposal table, and that a handed-off change "still waits for the user's commit". Both left the commit to the user rather than to the user's approval. `skills/propose-upgrades/SKILL.md` also forbade writing "an approval record by hand". Approval records ended when ask rules replaced the old commit gate, so the sentence described a mechanism that no longer exists. Two hook comments and the README's delegation-gate section named the commit gate as the source of an instruction. They now name rule 6 or the `git-commit` skill. No hook behaviour changed.

**Why rule 4 drops the prose fallback, and a mod enforces it (2026-10-05).** Rule 4 sent every decision through `AskUserQuestion`, but it still let a question with no fixed choices go under a final `## ❓ Open questions` heading. Two failures remained. A question left in prose still scrolled away in Mike's 80x50 terminal. And a dialog with no context right above it could not be answered without scrolling back to find what it was about. Mike decided to use the tool always. The fallback was never needed, because the dialog always offers Other, which takes a free answer. Rule 4 now says to ask every question through the tool, with its context in prose immediately above the call, in the same message. The intake skill's step 8 says the same. Mike also chose enforcement in code over prose. The README had argued that a semantic check on question delivery cannot be enforced reliably, so this reverses a deliberate choice. The `hooks/register.ts` module re-prompts once, through a Stop hook, when a reply leaves a question in prose. A deterministic filter and a classifier keep rhetorical questions, and questions inside code or quotes, from triggering it. The module also refuses an `AskUserQuestion` call that has no prose before it. Neither fires where nobody can answer the dialog: sub-agents, `claude -p` runs, the Index pipeline, and scheduled ticks. A re-prompt there would loop.

**Why a question is asked right after its context (2026-10-06).** Rule 12 put the item Mike acts on last, the question included, and made it restate what it depended on. Replies then explained a finding, moved on to other findings and a roster, and asked about the first finding at the end with its context restated. Mike wrote: "rather than restating context when the question is presented, ask the question right after the context is output for the first time, and dont wait until later to ask the question. this way the question stays with the relevant output for the user to read." He chose to make it a shipped rule. `AskUserQuestion` pauses the turn until Mike answers, so a reply can ask part of the way through and then go on. Rule 12 now says to ask each question right after the context it depends on first appears, and not to hold it for the end with that context restated. A verdict with no question can still close a reply. Only the placement of a question changed. Rule 1, rule 4, the 40-row budget, and the ban on "see above" references keep their meaning. The intake skill's step 8 and the README say the same. The mod in `hooks/register.ts` refuses an `AskUserQuestion` call with no prose before it, but it cannot tell first context from restated context, so this stays a prose rule.

**Why outward prose and replies never point at a file for content (2026-10-07).** Mike wrote: "make sure that generated output doesn't reference file content that is not visible in the output, for example when generating issue or PR bodies, dont reference a markdown file, because that is not accessible from within claude code." The reader of an issue, a pull request body, a comment, a commit body, a message to another session, or a terminal reply sees only that text. A pointer such as "see the plan at ~/.claude/plans/x.md", "details in scratchpad/pr-body.md", or "per vault note decisions/…" sends them to content they cannot open from where they read it, so the point is lost. This is the failure rule 12 already banned for earlier text the reply does not restate, extended to files. Rule 11 now says to restate in the text what the reader needs, and never to point at a plan, a scratchpad file, or a vault note for it. A path may still appear as a location the reader acts on, such as a file the change edits or a command to run, because the reader can act on it from where they are. Rule 12 says the same for terminal replies, and adds that a proposed commit message or body is shown in the reply, not named by its scratch file. The outbound prose guard enforces the outward half for `gh` and board-MCP bodies. It was `hooks/outbound-prose-guard.sh` then, and runs in the hooks module now (`hooks/mods/outbound-prose.ts`). Its `file-pointer` check targets those three path families only, so a repository path, a URL, and a command still pass. It reads what a body says, never which tool sent it, so it stays inside Mike's decision that guards do not steer tool choice. Rules 1, 4 and 6, the 40-row budget, and the placement of a question keep their meaning.

**Why a question shows every option it names (2026-10-14).** Orchestrators kept asking Mike to pick among options he had never seen. A sub-agent returned them in its hand-back, which Mike cannot see. The orchestrator then asked "A, B or C?" or "go with Watson's option 2?", or wrote a one-line summary above the dialog. The vault has recorded this since 2026-10-04, when labels like "B + A stopgap" pointed at a table Mike never saw. The dialog can also cover the prose, so a label must stand on its own. Rule 4 now says to render in the reply every option the question names, a sub-agent's included, with its grade and the recommendation, and to name each option in plain words, never only a letter or "Option N". The mod in `hooks/register.ts` enforces it with a structural check and no model call. It refuses a bare letter or "Option N" label. It refuses a question that names options, a table, grades or a sub-agent's proposal that the visible text of the reply does not show. In a forwarding turn, it also refuses a decision whose graded table and recommendation are not rendered above the call. A yes or no question and a question with no options pass.

**Why a typed request approves, and the gate reads the tree (2026-10-15).** Two failures Mike reported. Version 0.48 shipped the whole-tree rule as prose, and orchestrators still committed only the files their sub-agent's hand-back listed. The gate counted commits and checked the pick, but it never looked at the working tree, so a partial stage passed. It now reads `git status` where the commit runs and refuses a commit that leaves any file out, naming each one. A never-ship file may stay out only when the reply above the commit names its path, because the rule's one exception is a file Mike is told about. Second, Mike reversed the pick-only rule: "when i ask to commit and push and release, it does not need to prompt me after that. any action i specifically request should be deemed approved, be it just commit, or just push, or just create a release, or any combination of commands." He chose turn scope. The actions his prompt names are approved for the turn that prompt opened, and his next prompt ends them. A negated, deferred or question-form prompt approves nothing, and only his own prompts count. A `PermissionRequest` hook answers the dialog for those actions alone, so the `permissions.ask` rules stay the backstop for everything else. Work he did not ask to commit still waits for the "Commit it" pick. Rule 6 and the shared rules section now state both halves. A Holmes review then showed that a line like `git -c core.hooksPath=/x commit` would skip the dialog, so Mike narrowed it to plain forms: `git -C` only into this project or its worktrees, a push only of the current branch to its own remote or of the release tag, and `gh release create` only for this repository. In the same pass Mike reversed the 2026-10-05 choice to keep the permission prompt on plan writes: "agent should never ask permission to edit or create plans." Rule 6 and the shared rules section say never to ask before writing a plan file.

**Why a pick runs its commit with no prompt (2026-10-15).** After a "Commit it" pick, the `git commit` still raised the permission dialog, because f94ba45 kept that dialog as a backstop on pick-approved commits. Mike was asked twice for one action and rejected the backstop: once he has approved an action, he is not prompted again. The `PermissionRequest` hook now answers allow for the plain commit an unused pick approves, then for the push of that commit once it lands, in the same plain forms a typed request gets. A pick still covers one commit and its push, and never a release. Rule 6 and the shared rules section say so.

**Why a commit approval approves no push and no merge (2026-10-22).** Mike reported five failures of the gate in one day. A typed "go ahead and commit the changes" was asked again, because only a narrow shape counted. A "Commit and push" pick was refused for its label. An agent committed, pushed, and once merged a feature branch into main locally, all on one pick, when Mike had planned a pull request. Another session switched branches between a pick and its commit, and committed and pushed on the wrong one. A peer message that arrived while his pick was being delivered ended the pick. His rulings: "if i did not give permission to push, giving permission to commit is not implicitly giving permission to push", how a branch lands is his choice, and "all permission checks and gates should happen in core". So a typed request now counts in his own words, a pick counts by intent and approves one commit, a push and a merge into the default branch each get their own question, a pick is tied to the branch HEAD held when he picked, and only his own prompt ends an unused pick. Core took dev-team's commit guard, its commit subject check and its ten ask rules. Rule 6 and the shared rules section say so.

**Why the gate denies and the model asks through `AskUserQuestion` (2026-10-23).** On 0.51.0, in auto permission mode, the gate's `$.ui.ask` approval dialog resolved to its first option, "Yes, run it", without being drawn. Core's `PermissionRequest` hook then allowed the line, and two unapproved `git commit` probes ran in Mike's own turn. Outside auto mode the dialog appeared, and the model's own `AskUserQuestion` calls reached Mike in auto mode too. The docs say no mode auto-approves `AskUserQuestion`, so the `ui.ask` result looks like an engine bug that core cannot rely on. The test bench draws the dialog, so the suite could not see it. Mike has always wanted approvals to go through `AskUserQuestion`, and a hook cannot call it. So the gate now denies the line, and the deny spells out the question: alone in its call, with the exact line, the action, the repository and the branch, and for a commit the message and every file. His pick is the approval. A release, a history rewrite, `gh alias set` and an API write to the default branch had no pick before, so the deny records the line, and a "Run it" pick on a question that names it in backticks approves that one line, once. This overrules the 2026-10-22 decision to ask through `ui.ask` to save Mike round trips. A sub-agent cannot ask, so its release is now refused in every spelling, where before it asked through `ui.ask`.

**Why a question that carries its own context needs no prose above it (2026-10-23).** In a turn that forwarded a claude-code-guide result, three `AskUserQuestion` calls were refused. The refusals alternated between "no prose comes immediately before this call" and "render the options table", because two checks read two different spans of the reply. The transcript shows those calls had only thinking above them, so each refusal was right on its own terms, but neither said everything the next try needed. Mike ruled that a question carrying every detail he needs to decide drops the prose requirement: each label says what its option does, each description carries its grade and any warning, and nothing points at options, tables or grades shown elsewhere. A question that leans on context it does not carry still needs that context in the prose right above the call. One check now reads one span, the prose right above the call, and one refusal names every missing item at once, so a retry never meets a second refusal that asks for something else. Rule 4 says so.

**Why the memory server follows upstream 5.1.0, and a `write` needs an etag to replace (2026-10-23).** The bundled server wheel was 4.1.0, and `scripts/build-memory-wheel.sh` built it from Mike's fork by default. Every fork pull request had since merged upstream, and upstream main was 5.1.0. Mike chose to follow upstream from now on, so the build script now builds the upstream release tag by default, and the fork is only an option for testing a change. 5.0 refuses a `write` over an existing note unless it passes the `etag` of a `read` as `if_match`. The plugin keeps that default, because a blind replace is how a note another session had just written was lost on 2026-10-09. So the vault convention, the summary-writer and the memory-lint rescue now pass the etag when they replace a note on purpose. The server hung the same day while a full vault walk held its writer lock and iCloud downloaded thousands of evicted notes. That is an iCloud problem Mike is fixing in Finder. 5.x still runs the walk as one job on the single index writer, so index updates still queue behind a slow walk. It adds a switch to skip the walk at start, `MARKDOWN_VAULT_MCP_BOOT_REINDEX`, which the plugin leaves on.
